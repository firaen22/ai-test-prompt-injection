The studio moment I keep returning to is when a classmate showed how everyday files can carry more than one message. During peer demo day, they opened a markdown file that rendered cleanly in a reader but executed hidden JavaScript when opened in a browser — a polyglot file that behaved differently depending on the interpreter. What lingered wasn't the technical cleverness; it was the realization that trust in a file's content is conditional on the toolchain reading it. I had been treating "what the file says" as a fixed property, but the demo exposed it as a negotiation between format, parser, and context.

This shifted how I think about workflow design. In Week 4 we discussed how pipelines encode assumptions about input validity; in Week 5 we saw how evaluation metrics can miss failures that only appear under a different parser. The polyglot file is a concrete instance of both: a workflow that validates only one rendering path creates a blind spot, and an evaluation that checks only the intended output misses the alternate message. Now when I design a step that consumes external files, I ask which parsers might touch them downstream and whether the file's meaning is stable across all of them.

The trade-off is that defending against every parser variant bloats the workflow. Sanitizing for polyglots means either restricting accepted formats (reducing flexibility) or adding multiple validation passes (increasing latency and maintenance). In a low-stakes internal tool, that cost may not pay off; in a pipeline ingesting untrusted uploads, it's necessary. The decision belongs in workflow design, not as an afterthought in evaluation.
