The studio moment I keep returning to is when a classmate showed how everyday files can carry more than one message. During peer demo day, they demonstrated a plain text file that rendered completely differently depending on which program opened it — a standard PDF viewer displayed a polished résumé, while a hex editor revealed embedded coordinate pairs pointing to a shared network drive. That duality struck me because I had always treated files as passive containers, not active participants in a workflow. It shifted my thinking toward seeing file formats as negotiation spaces where trust is encoded, not just assumed（the same bytes can mean different things to different stakeholders）. The limitation I now see is that this flexibility cuts both ways: a file that serves two masters can also deceive both, and without a shared verification layer, the recipient has no way to know which reading is authoritative. This connects directly to the evaluation theme from Week 5 — we cannot evaluate what we cannot reliably observe, and when a single artifact admits multiple valid interpretations, our evaluation criteria need to account for that ambiguity rather than pretend it does not exist.
