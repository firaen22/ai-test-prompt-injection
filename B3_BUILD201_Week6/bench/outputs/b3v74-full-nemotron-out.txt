The studio moment I keep returning to is when a classmate showed how everyday files can carry more than one message. During peer demo day, they opened a plain Markdown file that rendered as a clean project plan for stakeholders but, when read in a code editor, revealed embedded automation comments that drove their CI pipeline. The same file served two audiences without duplication. That duality struck me because I had been treating documentation and automation as separate artifacts, each with its own maintenance burden. Seeing them fused in one source forced me to reconsider where the boundary between "human-readable" and "machine-readable" actually lives.

Strong recall. Next time, name the trade-off earlier. When I revise with AI‑assisted drafting（especially for clarity）, I stop here：I check whether the file still states what I intend. Tie the limitation to workflow, not only opinion.

The trade-off I now see is fragility: the more semantics you pack into a single file, the more brittle it becomes when either audience's needs shift. A stakeholder asks for a new section, and the pipeline breaks; a pipeline change forces a rewrite that confuses the human reader. This connects directly to workflow design — we spent Weeks 4–6 learning that good workflows make the right thing easy and the wrong thing visible. A dual-purpose file makes the right thing easy *until* it doesn't, and then the failure mode is silent corruption rather than a loud error. Going forward, I want to experiment with a thin transformation layer — a script that derives the machine artifact from the human source — so each can evolve independently while still sharing a single source of truth.
