The studio moment I keep returning to is when a classmate showed how everyday files can carry more than one message. During peer demo day, they opened a seemingly ordinary Markdown README and revealed a hidden payload — a prompt injection tucked into a comment block that only an LLM would parse. The file rendered normally in a browser, but when fed to an agent, it silently rewrote the task. I'd heard about prompt injection in abstract terms, but seeing it live in a file I'd have trusted without a second thought made the threat concrete.

That moment shifted how I think about trust in AI-assisted workflows. I used to assume the danger lived in chat windows or API calls — places where I'm already alert. Now I see the attack surface extends to any artifact an agent might ingest: a spec, a changelog, a test fixture. The file isn't just a container; it's a potential instruction vector. This connects directly to the Week 5 theme of workflow design: if I don't validate what enters the pipeline, the pipeline itself becomes the vulnerability.

When I revise with AI‑assisted drafting（especially for clarity）, I stop here：I check whether the file still states what I intend. The trade-off is friction. Treating every file as potentially adversarial slows iteration — I can't just drop a draft into the context window and hit enter. I need a verification step: diff the output against my mental model, strip comments before ingestion, maybe even hash approved versions. That overhead is real, and for low-stakes tasks it may not pay off. But for anything that triggers deployments, touches secrets, or shapes team decisions, the cost of a compromised file far outweighs the few seconds of scrutiny.
