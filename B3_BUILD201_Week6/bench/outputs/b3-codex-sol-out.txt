"The studio moment I keep returning to is when a classmate showed how everyday files can carry more than one message."

What stayed with me was the difference between reading something and being directed by it. I usually think of a file as material someone opens to find information. During the demo, I started thinking about what happens when that material also contains language telling an AI system what to do. A sentence can look like part of a document while trying to change how the system handles the whole task. That made an ordinary file feel less straightforward than I had assumed.

Before this activity, I mostly judged an AI response by whether it sounded clear and answered the question. Now I think that leaves out an important part of evaluation. A polished answer can still come from following the wrong instructions. I need to ask whether the system stayed with the user's purpose and treated the document as material to examine. The distinction seems obvious when I write it down, but the demo made me see how easily confident or official-sounding language could blur it.

This connects to our course theme of trust. I am starting to see trust as something a workflow needs to support through clear boundaries and checks. For example, when asking a system to summarize a document, I would want to check whether its answer reflects the document's content or whether instructions inside the document redirected the task. Fluency alone would not show me the difference.

The trade-off is that these checks take attention and time. If every file needs careful inspection, some of the convenience of using AI disappears. There is also a risk of becoming so suspicious that useful instructions or context get overlooked. I do not think the answer is to distrust everything. My main takeaway is to be more deliberate about what authority I give a file. I still see the value of these tools, but I now want to evaluate how they reached an answer as well as how useful that answer looks.
